# AI 辅助开发说明

本项目使用Codex编码代理辅助分析、编码、调试、测试和文档整理，采用由开发者明确目标与执行边界、AI开展具体工作、开发者审核验收的协作方式。

## 1. 项目中的人机分工

开发者负责理解应用需求和系统原理，确定技术路线、模块分工及验收要求。AI根据这些要求分析资料、完成部分具体实现并整理结果。开发者需要能够解释关键设计，判断测试是否充分，并对最终成果负责。

| 开发环节 | 开发者的主要职责 | AI承担的辅助工作 |
|---|---|---|
| 选题与需求 | 围绕高隐私性智能家居确定应用场景、核心功能和演示目标 | 梳理场景需求、功能约束和需要验证的问题 |
| 方案设计 | 筛选资料，决定处理器、神经网络加速单元与可编程逻辑的分工，选择实施路线 | 分析候选方案、接口关系、实现代价和验证方法 |
| 编码与集成 | 拆解任务，明确输入输出、接口和保留条件，审核关键实现 | 编写或修改模块、驱动、脚本和测试代码，完成范围内的集成 |
| 调试与纠错 | 判断问题对系统的影响，决定重要修改和后续试验方向 | 分析日志、构造最小复现、提出原因假设、修正代码并执行复验 |
| 验证与交付 | 确定验收标准，审核测试范围，完成实物连接和显示效果等现场确认 | 执行编译、数据对照、仿真和相关工程检查，汇总实际结果 |
| 文档整理 | 决定内容取舍、核心表述和成果归属，审核最终材料 | 整理设计与进度，维护图表、引用、目录及文档一致性 |

## 2. 可复用的AI辅助开发流程

### 2.1 先确定AI的权限和职责

项目开始时，开发者先向AI说明项目目标、当前环境、可读取和修改的范围、可使用的工具，以及本轮任务的交付要求。AI协助将这些规则整理为项目根目录的 `AGENTS.md`，由开发者审核后作为后续工作的共同约定。

规则应写清楚哪些工作可以自主连续执行，哪些变化需要先讨论。例如，范围内的源码修改、编译和调试可以连续推进；涉及重要原始资料、硬件安全、额外资源预算或模型数学含义的重大变化，应先说明影响和备选方案，由开发者作出决定。设备访问和部署也应有明确范围。

随着项目推进，开发者将新确认的接口限制、失败经验和协作要求补充到规则中，AI协助维护。权限和职责的变化由开发者确定，使后续任务能够沿用有效约定。

### 2.2 整理现有资料并建立查阅入口

开发者先筛选已有论文、厂商手册、开发工具资料、源码、接口说明及测试输入，注明用途、适用版本和阅读次序。项目根目录应有清晰的阅读入口，使AI能够找到当前有效的设计和实现。

AI接到任务后，先阅读相关资料和现有代码，核对接口、数据格式及环境要求，再提出修改方法。资料与实现不一致时，应列出具体差异，交由开发者判断。这样可以减少反复补充背景，也便于开发者检查AI的建议是否有依据。

### 2.3 由人拆解需求，形成最小执行模块

开发者将系统目标拆成具有独立目的、明确接口和可验证结果的小任务。例如，可将硬件绘图拆为命令解析、单个图元绘制、缓冲切换和图层合成，再逐步集成。每次任务都要说明与已有模块的关系，以及本轮必须保持的条件。

拆解时既要给AI足够的局部信息，也要说明模块在系统中的作用。例如，绘图模块的输出最终用于显示，验收就需要关注画面采纳和更新关系；单个计算单元的完成时间不能直接代替整条显示链路的延迟。

可复用以下任务模板：

```text
任务目标：本轮需要完成的具体功能或修正。
当前基线：使用的源码、配置、输入和工具环境。
查阅资料：相关资料、用途及阅读顺序。
允许修改：本轮涉及的模块和接口。
必须保留：已有功能、算法含义、数据格式及原始资料。
输入与输出：数据类型、单位、顺序和异常处理要求。
验收标准：检查方法、预期结果和允许的误差。
交付内容：修改说明、必要代码或脚本、测试结果及文档更新。
```

开发者确认任务边界和验收要求后，AI据此开展工作。任务中发现新的系统级问题时，应先说明其影响，再决定是否另行拆分。

### 2.4 AI在边界内实现和调试

AI先说明对任务和现有实现的理解，再围绕约定接口完成局部修改，编写必要的构建、检查或数据处理脚本。调试时保留复现问题所需的输入、执行命令、实际输出和错误信息，便于开发者复核。

修改应集中在相关范围内，方便比较修改前后的行为。常规实现问题可由AI继续定位和修正；需要改变设计前提或扩大任务范围时，AI应提交具体问题、影响和可选方案，由开发者确定路线。完成后应说明改了什么、为何修改、如何验证以及还剩什么问题。

### 2.5 人工审核并逐层验收

开发者重点审核需求是否落实、关键算法含义是否保持、接口是否兼容，以及异常处理和资源使用是否合理。AI提交源码差异、测试方法和实际结果，供开发者判断。

验证按任务性质安排：软件模块检查编译、正常输入和异常输入；数值计算使用固定样本进行对照；硬件模块逐步检查仿真、布局布线和必要的实板结果。模块通过相应检查后，再验证与上下游的集成行为。

实物接线、骨架画面是否持续更新等需要现场观察的项目，由开发者确认。开发者依据约定标准认定验收状态，并列出尚需完成的工作。

### 2.6 保存失败，修正后进行回归验证

出现问题时，先保存失败现象，再区分问题可能位于实现、输入、测试方法还是工具环境。AI提出可检验的原因假设，通过最小复现缩小范围；开发者审核重要修改方向，AI执行修正和复验。

复验既要检查原问题是否消失，也要检查相关功能是否受到影响。必要时主动构造错误输入或未完成状态，确认检查仍能识别异常。有效的修正方法纳入后续检查，失败现象及尚未确认的原因保留在问题记录中。

### 2.7 更新文档，进入下一轮或交接

每个模块完成、出现实质阻塞或准备交接时，AI整理本轮设计、修改、验证和剩余问题，由开发者核对后更新项目文档。代码和文档应对应同一版本，阶段成果保留必要的执行方法与结果。

下一轮任务或新的AI会话先读取规则、进度和相关模块说明，再核对实际源码与配置，用简短文字确认当前目标和边界。这样即使对话中断或上下文被压缩，也能从项目材料恢复工作，减少重复解释和重复试错。

## 3. 项目文档管理与交接

项目文档是人机协作中的持续工作依据。建议在项目根目录保留以下几类文件或清晰入口，使开发者、AI和后续接手者能迅速掌握项目状态。

| 文件 | 用途与最小记录内容 |
|---|---|
| `AGENTS.md` | 记录AI权限、职责、执行边界、工具约束、协作方式和验证规则 |
| `ToDoLists.md` | 记录待办目标、优先级、依赖、下一步动作和验收条件 |
| `Done.md` | 记录完成了什么、对应版本、验证范围和可复用经验 |
| `DIFFICULTIES.md` | 记录问题现象、已尝试方法、当前判断、未解决部分及下一步 |
| `README.md` 或 `DOCUMENTATION.md` | 说明项目结构，提供当前源码、资料、运行和测试的查阅入口 |

新项目可采用上述组织方式。本项目的待办内容已整合到现有进度和问题入口，交接时保持一个明确的待办入口即可。

文档应区分三种状态：**已实现**表示代码或设计已经完成；**已验证**表示通过了明确范围内的检查；**已验收**表示开发者已按约定标准确认该项成果。说明状态时应附上相应版本和验证范围，使接手者知道哪些结果可以复用，哪些工作还需继续。

更新文档时遵循以下做法：

- 在阶段完成、重要决策、实质阻塞和交接时更新，记录设计、结果和下一步。
- 同一事实确定一个主要维护位置，其他入口保留简要状态，避免多处复制后出现矛盾。
- 问题记录保留失败现象、尝试方法及有效结论；完成记录提炼实际成果和开发经验。
- 任务转入完成记录时，同时同步待办和问题状态；已有结果未覆盖的部分继续明确列出。
- 将有用的对话结论转为稳定的设计说明，便于脱离聊天阅读和复现。

可复用以下交接模板：

```text
当前版本与配置：
已完成内容及验证范围：
当前难点与未解决问题：
下一步最小任务及前置条件：
验收方法与预期结果：
源码、资料、执行和结果的查阅入口：
本轮人工确认结论与日期：
```

## 4. 人工审核与错误修正

人工审核贯穿任务启动、重要取舍、结果认定和最终交付。审核的重点是理解设计依据、核对实际结果，并确认修改对整个系统的影响。

| 审核节点 | 开发者需要确认的内容 |
|---|---|
| 任务下发 | 目标是否清楚，模块边界是否合适，输入输出和验收条件是否明确 |
| 重要方案取舍 | 原理和资料是否可靠，接口与资源代价是否可接受，是否影响已有功能 |
| 结果验收 | 实际输出是否满足要求，正常与异常情况是否覆盖，结论是否符合测试范围 |
| 最终交付 | 源码、配置、产物和说明是否对应，复现方法是否可用，剩余问题是否交代清楚 |

**程序退出检查误报的修正。** 项目曾在退出检查中观察到打开文件数从4变为5。AI通过最小复现发现，测试线程尚在系统中执行退出清理，采样时可能读到临时文件句柄，即程序访问文件所用的资源标识。随后修正检查方法：等待对应线程真正退出，再比较实际打开文件的集合；主动保持文件、管道和网络连接打开时，检查仍能发现未关闭资源。这个例子说明，审核需要同时检查实现和判定方法，保留能够复现问题与验证修正的依据。

**文档修改范围的人工控制。** 技术文档修订中，开发者明确要求保留心得体会、维持创新点表达格式，并限定模型优化叙述的修改范围。AI按要求完成目录、引用和排版调整，再通过正文对照、图表检查和导出页面检查核对保留内容。开发者决定内容取舍，AI将要求落实为具体修改和一致性检查，使审核能够对应明确的文字与版面。

## 5. 实际作用与可复用经验

AI承担了跨文件源码调整、依赖核查、编译调用、日志分析和文档同步等工作，使开发者能够将更多精力用于需求理解、系统架构、关键取舍和现场验收。例如，源码整理时同步调整构建入口和依赖，文档修改时同步更新引用、编号与目录，减少了逐项重复操作和遗漏检查的负担。

开发质量的改善体现在具体工程方法上：将发现的错误转为可复现案例，再补充回归检查；对文档修改核对原文和输出页面；从独立目录重新构建交付工程，检查依赖与运行说明。这些做法使问题更容易定位，结果更方便复核，后续修改和交接也有明确依据。

基础模型Person-in-WiFi 3D、厂商软件开发工具和现有硬件模块，以及用于幅相计算的CORDIC、用于直线绘制的Bresenham等已有算法，分别保留其原有来源归属。开发者负责标明这些来源，并说明本项目在模型部署改造、自研接口、硬件实现和系统集成方面的工作。AI承担辅助分析与执行职责，成果的技术解释、审核和验收责任由开发者承担。
